## 2. Режим «лише бот» на сервері

- Новий прапорець (назва — пропозиція) `bot --server`: `poll` + `Bot` без `start_site`
  (`__main__.py:694`), без `_daily_report`/`_alerts` у `tick` (`core.py:703-704`), без
  `_card_edit`/`site.edited`/`site.enqueue` — замість них запис у **вихідну чергу** (п. 3).
- База — своя `shafa.sqlite` на сервері, та сама схема (`db.connect` створює всі таблиці; `items`
  тощо лишаються порожні). Нова таблиця черги = міграція 16→17 у `db.py` — **потрібне рішення
  Архітектора** (тікет забороняє `db.py` без нього). Альтернатива без `db.py` — json-рядки в теці
  даних, але тоді атомарності «пост + запис у чергу» немає → раджу таблицю.
- Імпорт: `import shafa.bot.core` тягне `anthropic`, `robot.*` (без `playwright` — VERIFIED
  `python -X importtime`), RSS ≈ 81 МБ на Mac — у 1 ГБ влазить. Ставити `pip install -e .`
  (playwright ставиться як пакет, браузер не качаємо).
- `.env` сервера (лише назви): `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_CHANNEL_ID`,
  `TELEGRAM_CHANNEL_ID`, `TELEGRAM_SELLER_CHAT_ID`, `TELEGRAM_OWNER_CHAT_ID`, `SHAFA_ROOT_DIR`,
  `SHAFA_ASK_BUTTON`, `SHAFA_SITE_BUTTON`, `SHAFA_AI_WAIT_DAYS` (лише для тексту «піде до …»,
  `core.py:1263-1268`), `SHAFA_SITE_WAIT_DAYS` (теж для тексту). **Не потрібні:**
  `ANTHROPIC_API_KEY`, `SITE_INTEGRATION_KEY`, `SHAFA_SITE_SEND` (на сервері має бути вимкнено),
  усе робота. `SHAFA_DATA_DIR` — у systemd-службі (`config.py:88-99`; без неї Linux бере
  `~/.local/share/shafa`).
- **Часовий пояс сервера = Europe/Kyiv обов'язково:** `local_date` (`core.py:358-360`) пише
  `posts.date` місцевим часом сервера; Oracle типово UTC (**UNKNOWN**, перевірити `timedatectl`) —
  інакше дата поста зсунеться на 2–3 год (межа 7 днів ШІ, «піде до …»). Краще ще й передавати
  Unix-час у черзі, а місцеву дату рахувати на компі.

## 3. Обмін сервер → комп

Спільне для обох варіантів:
- Сервер пише **вихідну чергу** з наростаючим номером `seq`: `post` (номер, дата Unix, текст,
  `source=bot`, назва папки, `posted_at` для сайту, кількість фото), `edit` (номер, новий текст),
  `owner_cmd` (п. 5), `heartbeat`. Запис у черзі — в тій самій транзакції, що `posts`.
- Комп тримає у своїй базі «останній застосований `seq`». Тягне `seq > N`, застосовує в
  транзакції, потім **підтверджує** `N`. Повтор нічого не дублює: `posts … ON CONFLICT DO NOTHING`
  (`core.py:1061`), `site.enqueue … DO NOTHING` (`site.py:422`), папка — у тимчасову назву, перевірка
  sha256 файлів, потім перейменування; та сама папка вже є з тими самими файлами → пропуск.
- Фото на сервері не видаляються, доки комп не підтвердив, і ще 14 днів після (запас). Комп вимкнений
  тиждень — черга просто довша (45 ГБ диска; пост ≈ 1–5 МБ).
- При запуску `app` і кожні 10 хв (налаштування), лише коли програма відкрита.

**Варіант A — SSH (рекомендую).** Комп запускає системний `ssh` (Windows 10/11 має OpenSSH-клієнт —
**UNKNOWN** для її ноутбука, перевірити `ssh -V`) з окремим ключем лише для обміну. У
`authorized_keys` сервера ключ обмежено: `restrict,command="…/python -m shafa outbox --serve"` —
ключ не дає оболонки, лише дві дії: «віддай zip з `seq > N`» (у stdout) і «підтверджую N».
Відбиток ключа сервера — закріплений у `known_hosts` теки даних (`StrictHostKeyChecking=yes`).
+ нових портів немає (22 уже відкритий для Власника — **UNKNOWN**, з тікета випливає);
+ шифрування й автентифікація — готові, нічого свого;
+ сервер ніколи не ходить до компа; ключ скомпрометовано — можна лише читати чергу.
− `ssh.exe` з `pythonw` без вікна: лише `BatchMode=yes`, без паролів (перевірити на Windows-CI
  частково, наживо — лише на її ноутбуці);
− приватний ключ — секрет у теці даних, права як у `.env` (`icacls`); OpenSSH на Windows відмовляє
  ключам із «широкими» правами — треба точні ACL;
− ключ створюється на кожному компі окремо (Mac Власника, потім її Windows) — `transfer-pack` його
  не везе (правильно).

**Варіант B — HTTPS на сервері з токеном.** Маленький сервер (`http.server` за Caddy) з двома
адресами `GET /outbox?after=N`, `POST /ack`; заголовок з довгим токеном; комп — `httpx2`.
+ однаково на Mac і Windows, без зовнішніх програм; простий код клієнта.
− **новий відкритий порт 443**: правило в Oracle Security List + `iptables` на образі Oracle
  (**UNKNOWN**, як налаштовано), публічна поверхня атаки 24/7;
− TLS: потрібен домен для Let's Encrypt або самопідписаний сертифікат із закріпленим відбитком;
− токен у `.env` обох машин; витік — читання черги з будь-якого місця.

Відкинуто: Tailscale/Cloudflare Tunnel (ще одна програма на її ноутбуці й сторонній акаунт);
`scp` теки напряму без черги (нема підтвердження й ідемпотентності правок).

## 4. Що бот на сервері має знати від компа

- «Вже в черзі» (`core.py:1212`) і старт перегляду каналу (`channel.py:107-111`: `max(posts ∪
  channel_posts)`; порожньо → «не знайшов» без перегляду!) читають `posts`. На порожньому сервері
  BOT-015/016/017 зламаються. **Рішення без зворотного обміну:** одноразово при переході
  засіяти сервер номерами всіх `posts` (лише `post_id`, `source`, `date`; без текстів Експорту) і
  `channel_posts`. Після переходу нові пости з'являються лише через сервер (бот або її ручний пост →
  `channel_post` → сервер), тож його `posts` лишається повним.
- Решта (Картки, «опубліковано на Шафі», сайт) боту не потрібна — VERIFIED за таблицею п. 1.
- Залишок ризику: новий Експорт на компі (`scan --export`) додає лише старі пости — вони вже засіяні.
  Якщо колись комп створить пост сам — сервер скаже «у черзі» замість «уже в черзі»; дубля не буде
  (`ON CONFLICT DO NOTHING` на компі, папка — п. 3).

## 5. Комп без опитування; звіти й тривоги

- Налаштування (назва — пропозиція) `SHAFA_BOT_SERVER` (адреса/хост обміну): є → `app` не запускає
  бота (`web.py:858`), кнопки «Запустити бота» немає, `quit_all` не шукає `bot.lock`.
- Звіт, тривоги, сайт, `presence` — з процесу бота переїжджають у фоновий потік (чи окремий процес із
  замком) на компі: `Bot.tick`-частини `_daily_report`/`_alerts` + `site.start`. Усе це лише
  `sendMessage`/`forwardMessage`/`deleteMessage`/`editMessageText` — опитування немає.
- Панель і самоперевірка: стан бота — з `heartbeat` останнього обміну («на сервері, на зв'язку
  N хв тому»), а не з `bot.lock` (`health.py:253`, `web.py:842`).
- **Вхідні команди Власника (DRIFT-1) — потрібне рішення:**
  - (а) **через чергу (раджу):** сервер на `/zvit`, `/detali` і кнопки `actions.ACTIONS`
    відповідає «Прийнято — зроблю, коли програма на компі на зв'язку» і пише `owner_cmd` у чергу;
    комп при обміні виконує (`actions.handle`-логіка, правка повідомлення через
    `editMessageText`). Затримка — до періоду обміну; комп вимкнений — виконається пізніше.
  - (б) **без кнопок:** тривоги з компа без кнопок (BOT-011 втрачається), `/zvit` на сервері —
    «звіт надійде о 21:00 з компа».
- **Небезпека:** `poll` на 409 кидає `SetupError` і виходить (`run.py:156-159`). Якщо комп колись
  запустить бота, **обидва** отримуватимуть 409 → серверний бот впаде (systemd підніме, але комп
  теж). Тому заборона опитування на компі має бути в коді, не лише звичкою; на сервері —
  `Restart=always`.

## 6. Розгортання на сервері

У репо (`ops/server/`): `shafa-bot.service` (systemd: `User=ubuntu`, `Environment=SHAFA_DATA_DIR=…`,
`ExecStart=…/.venv/bin/python -m shafa bot --server --db … --root …`, `Restart=always`,
`RestartSec=10`, `MemoryMax=400M`); таймер нічної копії бази (`sqlite3 .backup`, 7 копій);
скрипт `install.sh` (venv, `pip install -e .`, служба); `docs/install-server.md`.
Командами Власнику: `timedatectl set-timezone Europe/Kyiv`; swap 1–2 ГБ (1 ГБ RAM, `pip`);
`python3.12-venv` (**UNKNOWN**, чи є в образі); `.env` — `nano` у теці даних + `chmod 600`
(секрети вводить сам, не в чат); ключ обміну в `authorized_keys`. Журнал — `journalctl -u shafa-bot
-n 50` (stdout бота). Оновлення: `git pull` у клоні сервера (приватний репо → read-only deploy key,
**рішення Власника**) або `git archive`-архів із Mac через `scp` → `systemctl restart shafa-bot`.

## 7. Перехід Mac → сервер без втрат і подвійних постів

1. Сервер готовий, служба **вимкнена**. На Mac — `quit` (бот гасне; `bot.lock` вільний).
2. Нова команда `bot-pack` (як `transfer-pack`): `bot_updates`, `bot_drafts`, `bot_draft_parts`,
   `bot_summaries`, `channel_posts`, номери `posts`, теки постів, де `comments='waiting'` (альбом
   ще не додано, `core.py:1398-1424`). `bot_updates` — **обов'язково**: останню пачку Mac
   обробив, але не підтвердив (`offset` підтверджується наступним `getUpdates`, `run.py:172`) —
   Telegram віддасть її серверу ще раз, дедуп `core.py:465-468` її пропустить.
3. `bot-unpack` на сервері → старт служби. `recover` (`core.py:1316-1339`) переводить
   `publishing` у `uncertain` без повтору — подвійного поста немає. Id чернеток ті самі — кнопки
   старих прев'ю працюють.
4. На Mac — `SHAFA_BOT_SERVER`, `last seq = 0`, перший обмін. Перевірка: тестовий пост у
   **тестовому каналі** → папка й `posts` на Mac.
Вікно простою — хвилини; повідомлення в цей час чекають у Telegram (до 24 год).

## 8. Ризики і що тестувати без мережі

Ризики: два опитувачі (п. 5); пояс сервера; черга не підтверджена → фото не видаляються (диск);
обмін обірвався посеред zip (ідемпотентність, тимчасові назви); правка поста прийшла раніше за
сам пост на компі (порядок за `seq`); папка `<номер>` уже є на компі (як `-бот` сьогодні,
`core.py:1159-1165`); кнопки тривог натиснуто, а комп вимкнений тиждень (застарілі команди —
перевіряти стан Картки, як `actions` уже робить); OOM на 1 ГБ; ключ обміну на її ноутбуці.
Тести (моки Telegram, тимчасові теки, без мережі): серверний режим не викликає сайт/звіт/тривоги;
запис у чергу атомарний із `posts`; повторне застосування тієї ж черги — без змін у базі й теках;
обрив посеред застосування → повтор; правка → `site.edited` + `changes.text_changed` на компі;
`owner_cmd` старий/повторний; `bot-pack`/`bot-unpack` + повтор `update_id`; `app` з
`SHAFA_BOT_SERVER` не спавнить бота; транспорт — підставний (`ssh` як підпроцес-заглушка).

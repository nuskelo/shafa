## Рішення Архітектора по OPS-002
1. Обмін — **варіант A, SSH**: окремий ключ обміну з примусовою командою в `authorized_keys` (`command="…",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding`) — ключ уміє лише «віддати нове з `seq` > N» і «підтвердити до N». Адмін-ключ Власника для обміну не використовується.
2. Вхідні команди Власника (`/zvit`, `/detali`, кнопки BOT-011) — **через чергу (варіант а)**: сервер відповідає «Прийнято — зроблю, коли програма на компі на зв'язку», комп виконує при обміні; застарілі/повторні — без шкоди.
3. **Міграція 16→17 у `db.py` дозволена** — лише нові таблиці (вихідна черга на сервері, `last seq`/вхідні команди на компі). Наявні таблиці не міняти. Тест: апгрейд копії бази v16 → v17 і повторний запуск без змін.
4. Час: сервер **Europe/Kyiv** (Власник поставить) **і** в черзі передавати Unix-час; місцеву дату рахувати на компі.
5. Оновлення коду на сервері: репо **публічне** → `git clone https://…` / `git pull --ff-only` + перезапуск служби, без deploy key.

## Що зробити (окремі коміти)
1. `bot --server`: `poll` + `Bot` без сайту, `presence`, звіту й тривог; правки/нові пости/папки/`queue_known`-події — у вихідну чергу атомарно з записом у базу (п. 2 проєкту).
2. Вихідна черга: `seq`, тип (новий пост, правка, видалено з каналу, `owner_cmd`, …), Unix-час, дані; фото — за шляхом, архівуються при віддачі. Команда сервера (для примусової команди SSH): «віддати після N» (zip/tar у stdout) і «підтвердити до N» (тоді можна прибирати старе).
3. `owner_cmd`: запис у чергу і відповідь «Прийнято…».
4. `bot-pack` / `bot-unpack` (п. 7 проєкту): `bot_updates`, `bot_drafts`, `bot_draft_parts`, `bot_summaries`, `channel_posts`, номери `posts`, теки з `comments='waiting'`; засів номерів постів для «вже в черзі».
5. Тести без мережі (п. 8 проєкту): серверний режим не викликає сайт/звіт/тривоги; атомарність; повтор віддачі — без дублів; `bot-pack`/`bot-unpack` + повтор `update_id`; міграція 17.

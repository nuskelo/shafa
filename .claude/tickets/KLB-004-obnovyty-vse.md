## Що зробити
1. **Команда** `python -m shafa robot --klubok-renew --db … [--human-click]`: замок робота, профіль Клубку, перевірка входу (`klubok_login`), знімок. Термін = найраніший `renew_date` її активних.
   - термін > зараз → нічого, «Наступне оновлення: ДД.ММ ГГ:ХХ», код 0, жодного GET `renew`;
   - термін ≤ зараз → `RenewTicket` → **один** GET рівно `https://klubok.com/renew/all` (`page.goto`, не клік по посиланню) → редирект на `/users/198135/manage` (очікувано) → пауза 5–10 с → новий знімок → перевірка: активних ≥ 90 % від попереднього **і** ≥ 95 % активних мають `renew_date` > зараз + 6 діб → тиха подія `klubok.renew` + `klubok_ads.renewed_at` для `published`; інакше гучна `klubok.renew_failed` «Оновлення на Клубку не підтвердилось — перевірте сторінку». Повтору в тій самій сесії немає (квиток одноразовий). 429 / капча / немає входу — стоп з кодом, як у публікації.
   - `--human-click` (перший живий запуск): робот відкриває `/users/198135/manage`, «Обновить все» тисне людина; guard пропускає цей один GET за квитком; далі знімок і перевірка як вище.
2. **Guard** (`robot/klubok_guard.py`): `/renew/all` — лише з живим `RenewTicket` і лише в `--klubok-renew` (або на початку сесії публікації, п. 3а); `/renew/{id}`, `?pg=renew-used`, `marksold` і решта — блок, як було. Публікація й знімок — без змін.
3. **Коли само:**
   а) сесія публікації Клубку: після знімка на старті термін ≤ зараз → спершу оновлення (та сама функція, той самий Chrome), далі публікація;
   б) фоновий щоденний запуск у програмі за зразком `rehearse.Nightly` (`app.py`): `SHAFA_KLUBOK_RENEW_AT` (типово «20:00», порожнє — вимкнено), лише коли `SHAFA_KLUBOK`, програма відкрита, робот вільний **і** за останнім знімком термін ≤ зараз + 1 год (або знімок > 24 год). Робот зайнятий / Mac спав — наступний тик того ж дня, далі наступного.
4. **Екран:** панель робота Клубку — рядок «Обновить все: наступне 24.11 о 16:33» / «оновлено сьогодні о 20:05 (1798)» / жовте «Прострочено з 24.11 16:33 — …причина…». Тривога Власнику (бот, як інші тривоги), якщо прострочено > 12 год.
5. **`klubok_fake`:** `/renew/all` → `renew_all()` + 302 на manage; сценарії: ок, «не оновилось» (`renew_date` ті самі), 429, без входу.

## Ітерація 1 · рішення по Фазі 0 (Архітектор · 17.11.2026)
Факт прийнято: «Обновить все» чіпає лише прострочені, у кожного оголошення свій термін (мить оновлення + 7 діб). Виправити `docs/klubok.md` (і факти цього тікета вище — не переписувати, досить розділу в docs).
- **(а) Коли:** щойно прострочене хоч одне — **не частіше одного GET `/renew/all` на місцеву добу**. Щоденні малі групи — нормально (запит безкоштовний, оголошення свіжі). Щоденний запуск: о `SHAFA_KLUBOK_RENEW_AT` і пізніше того ж дня (свій клас, без `GRACE`; позначка доби — лише після запуску команди); умова — за останнім знімком є `renew_date` ≤ зараз + 1 год **або** знімок > 24 год. Сесія публікації — так само, якщо сьогодні ще не оновлювали.
- **(б) Перевірка:** база — свіжий знімок **до** GET: прострочені P = `renew_date` ≤ зараз. Успіх: ≥ 95 % з P тепер мають `renew_date` > зараз + 6 діб **і** активних ≥ 90 % від знімка до. P порожнє, але посилання є (п. в) — успіх, якщо посилання після GET зникло. Решта — `klubok.renew_failed`.
- **(в) Так:** перед GET — читання `/users/198135/manage` (уже в `PAGES`), N з «Обновить все (N)». **Посилання немає → GET не робимо** (подія тиха: «прострочених немає»), навіть якщо знімок каже інакше. Є → GET. N і |P| — у журнал сесії й подію (розбіжність — не помилка). `--human-click`: людина тисне саме це посилання; без нього людині нічого не пропонуємо.
- **HYP-1** (живі `renew_date` після 17.11) — додатково, не блокує: щойно Власник натисне «Перечитати мої оголошення», глянь розподіл і допиши в звіт.

# Клубок — проєкт змін (Архітектор · 10.11.2026)

Мета: пари Вікторії, схвалені в програмі, автоматично йдуть ще й на Клубок (klubok.com).
Одна перевірка Картки — для обох сайтів. Темп 10 → 20 → 30 пар/день, спершу зимове.
Дослідження: проєкт Shafa `claude/klubok-analiz-10-11.md`, `claude/klubok-doslid-10-11.md`; сторінки редагування — `~/klubok-4` (не в репо).
Цей файл — `docs/klubok.md` (перенесено в KLB-001; далі його ведуть тікети KLB-002…005).

## Рішення Власника (10.11)
1. Піврозмір → **обидва** цілі (38,5 → 38 і 39).
2. Пост зник з каналу → оголошення в список **«Схоже, продано»**; лише після «Так, продано» Вікторії програма знімає його з Клубку і більше не оновлює. Без підтвердження — нічого.
3. Зміна ціни/тексту в каналі після публікації на Клубку — **не чіпаємо**.
4. З дня запуску Вікторія сама на Клубок не виставляє (дату — при запуску).

## Принципи
- **Шафа не змінюється.** `items.status` — лише Шафа. Клубок має **свою таблицю** зі своїм станом і id.
- **Без ШІ.** Поля Клубку рахує код з Картки (вона вже перевірена) і тексту поста.
- **Захист як у Шафи:** свій `guard` (клік, мережа), квиток на одну публікацію, підставний Клубок для тренувань. **На Клубку небезпечні дії — GET-посилання** (`/renew/all`, `?pg=renew-used`, `?pg=marksold`): guard блокує їх і для GET (KLB-004: `/renew/all` — лише за одноразовим квитком); навігація — лише за списком адрес.
- **Робот Клубку — окремий профіль Chrome** (`<дані>/klubok-profile/`), але **той самий замок** `robot.lock`: ніколи два Chrome одночасно (слабкий ноутбук).

## Що в Картці → що на Клубку (код, `src/shafa/klubok/fields.py`)
| Клубок | Звідки |
|---|---|
| Название (`item_name`, ≤ 100) | `title` Картки (формат той самий: «… N розміру в … стані») |
| Описание (`text`) | перше речення поста (без ціни) + порожній рядок + `description` Картки (її правки діють) |
| Стоимость | ціна **з поста** (`rules.price_from_text`), не ціна Шафи |
| Категорія (3–4 рівні) | таблиця «група + тип Шафи + сезон → шлях Клубку» (`klubok/category.py`), id — зі знімка |
| Пол (`sex`) | лише дитячі категорії (у дорослих поля немає): `rules.said_gender` — дівчинка 0, хлопчик 1, інакше 2 «Любой пол» |
| Состояние | «Новий» → 1 «Новое», інакше 0 «Б/у». «Сток» — ніколи |
| Размер (`size[]`) | цілі; піврозмір → обидва; значення мають бути в списку розмірів категорії |
| Цвет | перший колір Картки за таблицею UA → ключ Клубку; «Різнокольоровий» або ≥ 3 → 99; немає відповідника → не ставимо |
| Бренд | `brand` Картки; з підказки Клубку — пункт «Бренд (Кирилиця)», чий початок = бренд; немає — вільний текст (живу поведінку перевіряє KLB-003) |
| Фото | порядок Картки, ≤ 15, **по одному**, кожне після завершення попереднього; звірка порядку з `formData.images` |
| Характеристики, доставка, служби | не чіпаємо (за замовчуванням, як у неї) |

Чого не вистачає → Картка на Клубок не йде, причина-код (`klubok_no_category`, `klubok_size`, `klubok_no_price`, `klubok_title_long`). Шафи це не зачіпає.

## Таблиця категорій
Точна таблиця «група + тип Шафи + зима → лист Клубку (id)» — у коді `src/shafa/klubok/category.py` (зі знімка `categors.json` 10.11; назви шляху кожного листка там же, `klubok-catalog` відмовляється збирати знімок, якщо дерево на сайті змінилось). Решта (одяг, аксесуари крім сумок і гаманців) — v1 на Клубок не йде.

Рішення KLB-001 (Ітерація 1, 10.11): чоловічі сумки — за полем `gender` Картки «Для чоловіків» → `Мужское / Аксессуары / Мужские сумки` (1000990), гаманці/портмоне → `Портмоне, кошельки` (1000998); барсетки — завжди 1000990; малюки «Босоніжки» → «Летняя обувь» (1000391); авоськи, органайзери, кейси для косметики, косметички, аксесуари для сумок, картхолдери, ключниці, затискачі, візитниці → `klubok_no_category`. Тип «Сумки» з «маленьк…» у назві → «Клатчи и маленькие сумки». Кольори — лише таблиця в коді (`klubok/fields.py`), знімок їх не бере. Підказка бренду — єдине посилання, яке робот може натиснути: `a.dropdown-item` з `href="#"` усередині `#filter2` (`robot/klubok_guard.py`).

## Черга й ліміт (KLB-002, зроблено — `src/shafa/klubok/queue.py`)
- **Кандидат:** `items.status` `approved`/`published`, не очищений архів, пост > `SHAFA_KLUBOK_FROM_POST` (типово 7200), рядка `klubok_ads` немає або він `queued`/`skipped` (крім її «Так, дубль»). `publishing`/`problem` Шафи — ні.
- **Вердикт** (`plan` — нічого не пише; `sync` — пише, чіпає лише `queued`/`skipped`, рядки Карток, що вже не кандидати, видаляє; «Скасувати схвалення» прибирає `queued` одразу): `skipped` з кодом `fields.ad` (`klubok_no_category`, `klubok_size`, `klubok_no_price`, `klubok_title_long`, `klubok_no_title`, `klubok_no_photos`), `klubok_post_gone` (нічна перевірка: пост зник, `publish.known_gone`), `klubok_post_done` (інша Картка поста, не сестра-розмір, уже `publishing`/`published`/`sold_asked`/`sold`/`removed` чи `problem klubok_uncertain`); `problem klubok_duplicate` (нижче); інакше `queued`.
- **Порядок:** зимове (сезон містить «Зима»; порожній — з тексту) → інше → лише «Літо»; усередині — старіші пости (`posts.date`, далі `items.id`).
- **Ліміт доби** `SHAFA_KLUBOK_DAILY_LIMIT` (типово 10, 1–30): спроби за місцеву добу за `klubok_ads.publish_started_at` — спільна `publish.started_on` (та сама, що й у Шафи). Ліміти незалежні. Спроба, що повернулась у чергу (`release`), лишається в ліміті; якщо ту саму Картку запустити знову того ж дня, `start` перезапише час — дві спроби однієї Картки за добу рахуються як одна (похибка ≤ 1 на добу, KLB-003 DRIFT-3).
- **`take(conn, root, today, post_id=None)`** → `Taken(cards, code)`: порожньо з причиною, коли Клубок вимкнено (`SHAFA_KLUBOK`, типово ні), знімка її оголошень немає чи він старший за 24 год (`klubok_snapshot_old`), ліміт вичерпано, у черзі нічого (`klubok_queue_empty`); інакше `sync` і по порядку до ліміту, кожна Картка ще раз перевіряється на дубль перед видачею. `post_id` — лише Картки цього поста (фільтр до обрізання за лімітом).
- **Стани:** `start` (`queued → publishing`, `publish_started_at`, `session_id`), `release` (`publishing → queued`: запит публікації точно не пішов; `publish_started_at` лишається), `published` (`klubok_id`, `url` — може бути NULL, його допише знімок), `problem`, `recover` (`publishing → problem klubok_uncertain` «Перевірте на Клубку, чи опубліковано», повтору немає) — кожен в одній транзакції з умовою на поточний стан.
- **Місце в черзі** (`place`, KLB-003 D7): лише рядки `queued`, порядок як у `plan`, без пошуку дублів, без `fields.ad` і без запису (на синтетиці 1787 оголошень × 48 у черзі — ≈ 7 мс замість ≈ 0,3 с). Картка без рядка — «у черзі» без номера.
- **Дублі** (`src/shafa/klubok/dup.py`): її активні (`klubok_listings`, `sold = 0`) і виставлені програмою (`klubok_ads` `publishing`/`published`). Правило — `listings.similar`/`sizes_close`/`prices_close`: розміри оголошення — з назви («38,5 розміру», «27-28 розміру», «40,5 размера»), бренд — `brand` рядка, а якщо NULL — бренд Картки (без уточнення в дужках, лише літери й цифри) **міститься в назві**; **KLB-010:** у назвах обох є номер моделі (цифри токена, не розмір, не рік, не устілка/ціна: «237», «530», «gel-1130» = «1130») і вони різні — не дубль; Картка без бренду — дубль лише при тому самому підтипі (рюкзаки / сумки / гаманці / клатчі / черевики / чоботи / кросівки / туфлі / тапочки…, `dup.subtype`) і ціні ±25 % (з брендом — ±40 %, як було); «нові» ≈ «в ідеальному стані» і 38,5 ≈ 38 не звужуються (на копії 12.11 повний перерахунок: 161 → 160 дублів з 394 Карток Шафи — решту вирішує людина в рядку «Проблем»); категорія — лише коли `category_id` відомий (перший рівень Женское/Мужское/Детское); невідоме не перешкоджає (сумнів — Проблема). Сестри-розміри поста й оголошення Карток того самого поста — не дублі. Кириличних назв брендів у знімку Шафи немає. Рішення на Картці: «Інша пара — виставити» → `dup_ok_at`, `queued`, дублі більше не перевіряються; «Так, дубль — не виставляти» → `skipped klubok_dup_yes` (назавжди), її оголошенню без поста — `post_id` Картки.
- **Фото** (`folders.photo_folder`): `item_folder`, а для опублікованого на Шафі — `<Головна>/Опубліковано/<папка>`. `purge_published` і `borh.purge_photos` не стирають фото поста, поки `queue.needs_photos`: рядок `queued`/`publishing`/`problem` або кандидат без рядка — **незалежно від `SHAFA_KLUBOK`**. Уже стерті — `skipped klubok_no_photos` (TD-070: брати фото з оголошення на Шафі).
- **Стать дитячого:** розділ Картки («Для дівчаток» 0, «Для хлопчиків» 1), інакше слово в тексті, інакше 2.
- **Екран:** на Картці рядок «Клубок: у черзі · місце N / не піде: … / публікується / виставлено ДД.ММ.РРРР · Відкрити на Клубку / Проблема: …» (коли Клубок увімкнено або рядок уже є; GET нічого не пише), для дубля — назва й посилання схожого і дві кнопки; над Проблемами — «Клубок: Проблеми» (лічильник вкладки — лише Шафа). Налаштування — блок «Клубок».
- **Пробний прогін:** `python -m shafa klubok-queue --db <копія> --root <Головна> [--today РРРР-ММ-ДД]` — файл `mode=ro`, копія в пам'яті мігрує, файл не змінюється; ≤ 60 рядків.

## Хвилі й Картки «лише Клубок» (KLB-008 — `klubok/waves.py`, `klubok/importer.py`)
- **База 19** (крок 18 → 19 — `db._waves`, одна транзакція: обрив лишає 18): `items.only_klubok` (0/1, типово 0) і `klubok_waves (post_id PK, wave 1|4, kind, added_at)`. Немає рядка хвилі → хвиля 2 (пост новіший за `SHAFA_KLUBOK_FROM_POST`; перший пост бота — 7015, Влад ставить межу 7014). `sync`/`forget` таблицю хвиль не чіпають.
- **Картка «лише Клубок»:** `klubok-<N>`, фото й текст поста в `<дані>/klubok-old/<N>/` (`1.jpg`, `текст.txt`), у Головній нічого (`list_folders` пропускає `klubok-…`). Шафа її не бачить: вкладки й лічильники (`review.counts`/`list_tab`), кнопки Шафи (`review.act` → `only_klubok`), сторінка `/item/N` (404), черга робота (`publish.queue_rows`), `rehearse`, dry-fill (`form.find_card`), бот (тривоги, «Що сталось»), щоденний звіт, `scan` (не «Папку не знайдено», не в підсумку), `changes.sync_photos`. ШІ (`fill`, `batch`) — як звичайну (ліміт «старих наперед» Шафи на неї не діє). Пост зник з каналу — в Архів, як у Шафі (`archive_gone`); `import-old` такий пост пропускає з рядком «Є Картка лише Клубок».
- **Схвалення:** `review.approve_klubok(conn, id)` — `review` → `approved` лише для `only_klubok = 1` (кнопка — вкладка «Клубок», KLB-009).
- **Кандидат черги:** Картка Шафи `approved`/`published` з постом > межі **або** з хвилею; Картка «лише Клубок» — `approved` і з хвилею. **Порядок:** хвиля ↑, далі як раніше (зимове → інше → лише літнє, старіші пости першими); так само `place` і `needs_photos`.
- **Запасне фото** (`fields.spare_photo`): у Картки немає фото (стерто) — `<дані>/klubok-old/<N>/1.jpg`, інакше `klubok_no_photos`.
- **Імпорт** `python -m shafa klubok-import --export <тека Експорту> --wave 1|4 [--dry-run] [--db …] [--root …]`: пости ≤ межі; тип — `waves.kind` за першим рядком (KLB-010: сумки → домашнє, якщо «тапочки/капці» раніше за інше взуття → одяг й аксесуари — рукавиці, шапки, шарфи, хустки, жилетки…, якщо в рядку немає слова взуття → зима → туфлі → демі → спорт → літо → інше; на Експорті Каналу змінилось 19 постів, усі — тапочки/рукавиці/одяг); хвиля 1 — зима/демі/сумки, 4 — спорт/літо/туфлі/домашнє, одяг/інше — ні. - **Фото:** dHash 64 біти. Її мініатюра в знімку — 158×158, центральний квадрат фото, тому наше фото теж обрізаємо до квадрата. Наші — усі фото Картки (≤ 15) + фото поста з Експорту; виставлене програмою — фото тієї Картки. Відстань ≤ **T1 = 4** → дубль. Виміряно на копії 12.11: 11 з 84 на відстані 0–1 (усі — через фото поста з Експорту), у 19 050 чужих парах мінімум 6. Більша відстань нічого не доводить.
- **ШІ:** `dup.Judge(site="klubok")` — інструкція `prompts/duplicate-klubok.md`, ціна з поста, без факту про інший пост; наше фото — найближче за відбитком, її — велике `/l/` (1024×768, адреса з `/m/` лише за точним шаблоном; не вийшло — мініатюра).
- **Рішення:** хоч один дубль (фото чи ШІ `yes`) → `skipped klubok_dup_yes`, текст «Дубль — …», її оголошення знає пост; усі `no` → у чергу як «Інша пара» (`dup_ok_at`, текст «Інша пара — ШІ: …» живе після `sync`; будь-яка інша стара причина після `skipped` → `queued` переписується); кандидатів немає → «Інша пара — схожого на Клубку вже немає»; > 3 кандидатів чи оголошення програми ще публікується → людині без ШІ (збіг фото — однаково дубль); інакше людині зі словами ШІ.
- **Тимчасове** (мережа, 5xx, бюджет ШІ, немає ключа, ліміт запитів) — без маркера, наступного разу знову. **429/403** від `img.klubok.com` — стоп проходу (подія `klubok.dup_stop`). Фото — лише `https://img.klubok.com/`, GET без cookies, ≤ 5 МБ, `image/*`, пауза 0,5–1 с, кеш `<дані>/klubok-photos/`.
- **Слід і відкат:** тиха подія `klubok.dup_auto`; «Ще ▸ Архів» — група «Дубль — вирішила програма» з посиланням на її оголошення й кнопкою «Ні, це інша пара — виставити» (`queue.undo_auto_dup`); «Схвалені» — мітка «Інша пара (ШІ)»; над «Проблемами» — «Програма вирішила: X дублів, Y інших пар · вам лишилось Z».

## «Обновить все» (KLB-004)
**Факт (Фаза 0, файли 10–12.11):** «Обновить все» — посилання `<a href="/renew/all">Обновить все (N)</a>` на сторінці керування `/users/198135/manage`; `GET https://klubok.com/renew/all` оновлює **лише прострочені** оголошення й повертає на сторінку керування. N — скільки прострочено (10.11: «Обновить все (1785)» при 1787 активних; два свіжих не зсунулись). У кожного оголошення свій термін: `renew_date` у `get-items` = мить оновлення + 7 діб. Прострочених немає — посилання немає. Безкоштовне: платне поруч — «Сделать горячим» (`/payment/<id>`), guard його блокує. Що робить GET, коли прострочених 0, — невідомо, тож без посилання GET не робимо.
- **Коли:** щойно прострочене хоч одне, **не частіше одного GET на місцеву добу** (щоденні малі групи — нормально). Хто: `python -m shafa robot --klubok-renew --db … [--human-click]`; початок сесії публікації (KLB-013: **до** знімка сесії, до першої Картки, той самий Chrome); щоденний запуск у програмі (`klubok_renew.Daily`, потік `app`): о `SHAFA_KLUBOK_RENEW_AT` (типово 20:00, порожнє/`off` — вимкнено) і пізніше того ж дня, лише коли `SHAFA_KLUBOK`, робот вільний і за останнім знімком є термін ≤ зараз + 1 год (або знімок старший за добу); робот зайнятий / Mac спав — наступний тик того ж дня; позначка доби (`klubok-renew-daily`) — лише після запуску.
- **Як (`robot/klubok_renew.py`, KLB-013):** вхід (`#user_id`) → знімок «до» (не вдався — **не стоп**, лише нічого не записано й P невідоме; 429 — стоп) → сьогодні GET уже був (`klubok-renew.json` у теці даних) — нічого → читання `/users/198135/manage` (`fetch` усередині сторінки): посилання немає — нічого (найраніший `renew_date` > зараз — «Наступне оновлення: ДД.ММ ГГ:ХХ», інакше тиха `klubok.renew_skip`; знімок «до» не вдався — стоп з його кодом) → позначка доби → **один** `page.goto` рівно на `/renew/all` за `RenewTicket` (`--human-click`: робот відкриває сторінку керування, тисне людина, до 10 хв) → пауза 5–10 с → знімок «після» (не вдався — стоп) і сторінка керування. Сесія публікації: «Обновить все» записало знімок — свого не робить; `klubok_snapshot_drop`, а посилання «Обновить все (N)» є, — текст «Схоже, оголошення прострочені (N) — потрібне „Обновить все“».
- **Перевірка (KLB-013):** P — id вкладки «Обновить» за знімком до GET (знімка немає — N з посилання). Успіх — посилання після GET зникло (чи N після ≤ 5 % від N), у «Обновить» лишилось ≤ 5 % від P, активних ≥ 90 % від знімка до, і (коли id з P відомі) ≥ 95 % з них мають `renew_date` > зараз + 6 діб. Успіх — тиха `klubok.renew`, `klubok_ads.renewed_at` для виставлених програмою; інакше — гучна `klubok.renew_failed` «Оновлення на Клубку не підтвердилось — перевірте сторінку». Повтору тієї ж доби немає. 429 / немає входу / знімок не вдався — стоп з кодом, як у публікації.
- **Guard:** `RenewTicket` пропускає один GET рівно `https://klubok.com/renew/all` (без запиту, фрагмента, порту); другий — блок; квиток — лише в `--klubok-renew` чи на початку сесії публікації (до квитка Картки), один на сесію. `/renew/{id}`, `?pg=renew-used`, `marksold`, POST `manageAction` — блок завжди.
- **Екран і тривога:** панель Клубку — «Обновить все: наступне 24.11 о 16:33» / «оновлено сьогодні о 20:05 (1798)» / «прострочено з 24.11 16:33 — <причина>» (жовте — понад 12 год чи оновлення не підтвердилось); стан робота «Робот натискає «Обновить все»». Бот: прострочено > 12 год — одна тривога Власнику на термін (`alerts._renew_events`).

## Автостарт: Клубок виставляє сам щодня (KLB-014 — `klubok/auto.py`, `robot/klubok_auto.py`)
- Кнопка «Старт» лишається, але щодня натискати її не треба. Потік `klubok-auto` у `app` (`klubok_auto.Auto`, за зразком `klubok_renew.Daily`) раз на хвилину запускає **той самий процес, що кнопка** (`klubok_control.start_args` — одна функція для кнопки й автостарту: `--klubok-publish --db … --root … --limit min(left, 30)`, журнал `klubok-run.log`). «Обновить все» сесія робить сама на початку (KLB-013).
- **Умови (усі):** `SHAFA_KLUBOK` увімкнено; `SHAFA_KLUBOK_AUTO` не вимкнено (типово так; `0`/`ні`/`off` — ніколи); автостарту цієї місцевої доби ще не було; сесія Клубку, що закінчилась сьогодні, зупинилась не гучно (`klubok_publish.LOUD`: капча, невпевнено, немає входу, 429, знімок, заборонено, помилка — питання людини, тривога про це вже є); робот вільний (`lock.busy`, зайнятий — наступний тик); `klubok_control.state`: `can_start` і `left ≥ 1`; **і одне з двох:** (а) сьогодні закінчилась сесія Шафи спокійно (`sessions.site = 'shafa'`, `stop_code` `done`/`limit`/`stop` чи порожній без причини — як `publish._announce_end`) — Клубок іде одразу після неї; (б) настала `SHAFA_KLUBOK_AUTO_AT` (типово 21:00; порожнє/`off` — лише спосіб (а)).
- **Позначка доби** — `klubok-auto.json` у теці даних (`day`, `at`, `session`), пишеться **в момент запуску**; номер сесії дописується наступним тиком, коли сесія з'явилась. Один автостарт на добу: процес, що одразу впав, сьогодні вдруге не стартує. Ручний «Старт» автостарт не блокує й навпаки — їх обмежує лише ліміт доби (`SHAFA_KLUBOK_DAILY_LIMIT`, типово 10).
- **Панель Клубку:** «Автостарт: сьогодні після сесії Шафи або о 21:00» / «запущено сьогодні о 21:34» / «вимкнено» / «сьогодні не буде — сесія Клубку зупинилась з помилкою (код)» (жовте). Налаштування, блок «Клубок»: «Виставляти на Клубок самому щодня» і «Якщо сесії Шафи не було — запустити Клубок о».
- Програма має бути відкрита (потік у `app`); Mac спав / робот зайнятий — наступний тик того ж дня.

## Дитяче взуття, повторення форми, запасне фото (KLB-015 — `robot/klubok_form.py`, `klubok/queue.py`, `web.py`)
- **Причина «немає «Детское»» (22.11, пост 295):** гонка. Списки категорій приходять із `/api/1/categors` після відкриття форми, а `_select` дивився на ще порожній `#category`. Дерево Клубку не змінилось (живий вивід: 44 листки знімка збігаються з 469 вузлами).
- **Тепер:** кожен рівень категорії чекає потрібну опцію до `SELECT_WAIT` (15 с, опитування 0,25 с); не з'явилась — форма відкривається знову **один раз** і шлях проходиться з початку; лише тоді `klubok_field_missing` з переліком наявних опцій (≤ 12). Підставний Клубок: сценарії `late_categories` (3 с) і `late_once` (перше відкриття без категорій). Розміри й кольори (`_choose`) уже чекають `FIELD_WAIT` (5 с) — їх не міняли.
- **«Спробувати ще раз»:** Проблеми форми **до кліку** (`queue.BEFORE_CLICK`: `klubok_field_missing`, `klubok_verify`, `klubok_photos` — запит публікації не йшов) → `queued` (`queue.retry_form`, дія `klubok_retry_form`; кнопка в рядку «Проблем» і на Картці; не під час роботи робота). `klubok_uncertain`, `klubok_captcha`, дублі — ні: лише «перевірте, чи опубліковано».
- **Запасне фото на екрані:** вкладки Клубку (`/klubok/thumb|photo/<id>/<n>`) беруть фото Картки з диска, інакше `fields.spare_photo` (`<дані>/klubok-old/<N>/1.jpg`); на Картці підпис «фото з Експорту», без запасного — «немає фото». Шлях лише з бази й `post_id`. Шафа (`/thumb`, `/photo`) без змін. Причина «немає фото»: у еталонів `borh-<N>` рядки `photos` є, а файли стерто (PHOTO-001) — Шафа не мала що показати.

## «Схоже, продано» (KLB-005 — `klubok/sold.py`, `robot/klubok_marksold.py`)

(б): відповідь — в `asked_at` (`<час>|yes` / `<час>|no`; база 19 без міграції, окремої колонки відповіді немає).

## Її оголошення ↔ пости за фото (KLB-016 — `klubok/link.py`)
- **Навіщо:** пост відомий лише в оголошень, які виставила програма (і дублі); решту вона ставила руками → без поста KLB-005 не бачить продажу.
- **CLI (Власник; автоматики у фоні немає):** `python -m shafa klubok-link --export <тека Експорту> [--dry-run] [--db …] [--root …]` → звіт ≤ 60 рядків (зіставлено / перепост / неоднозначно / без збігу; нові — пост зник / живий / нічна перевірка не бачила; «Схоже, продано»; відомий пост ≠ за фото; список TD-077). `--dry-run` — копія бази в пам'яті, файл груп і подія не пишуться. Експорт — лише Каналу (`export.check_chat`). Клубок 429/403 — нічого не записано, код 1.
- **Фото:** її — мініатюра `/m/` (`photo_dup.Photos`, кеш `<дані>/klubok-photos/<id>.jpg`, лише `img.klubok.com`, пауза 0,5–1 с); поста — Експорт (1 фото) + усі фото Карток (Головна / `Опубліковано` / `borh/<N>` / `klubok-old/<N>`). Відбиток — `photo_dup` (центральний квадрат, dHash 64, T1 = 4).
- **Правило B (рішення 23.11):** кандидати ≤ T1; d = 4 — лише коли текст поста не суперечить назві (бренд латиницею й розмір ±0,5, якщо відомі з обох боків), d ≤ 3 — без тексту. Група = найближчий + кандидати, що між собою ≤ T1 **і** з тим самим текстом (бренд спільний чи обидва без, розмір ±0,5 чи невідомий). Кандидат поза групою з відривом < 3 → «неоднозначно» (нічого не пишемо). Прив'язка — **найновіший** пост групи; `post_id` пишемо лише в NULL. Подія `klubok.linked` (тихо; `reposts`).
- **Група перепосту — `<дані>/klubok-link.json`** (`{"<id>": [пости від найновішого]}`, лише групи ≥ 2 постів із `post_id` оголошення), переписується цілком кожним записом (тимчасовий файл → заміна). `sold.py`: пост зник, але інший пост групи живий (нічна перевірка бачила, не зник) — не питаємо; файлу немає чи він битий — питаємо (людина однаково підтверджує). Таблиця — TD-081.
- **Копія 22.11:** 1826 активних → 614 зіставлено (505 один пост, 109 перепостів), 6 неоднозначних, 1206 без збігу (531 старші за Експорт, каталожні фото); нових «Схоже, продано» — 7.

# Клубок — проєкт змін (Архітектор · 10.11.2026)

Мета: пари Вікторії, схвалені в програмі, автоматично йдуть ще й на Клубок (klubok.com).
Одна перевірка Картки — для обох сайтів. Темп 10 → 20 → 30 пар/день, спершу зимове.
Дослідження: проєкт Shafa `claude/klubok-analiz-10-11.md`, `claude/klubok-doslid-10-11.md`; сторінки редагування — `~/klubok-4` (не в репо).
Цей файл — `docs/klubok.md` (перенесено в KLB-001; далі його ведуть тікети KLB-002…005).

## Рішення Власника (10.11)
1. Піврозмір → **обидва** цілі (38,5 → 38 і 39).
2. Пост зник з каналу → оголошення в список **«Схоже, продано»**; лише після «Так, продано» Вікторії програма знімає його з Клубку і більше не оновлює. Без підтвердження — нічого.
3. Зміна ціни/тексту в каналі після публікації на Клубку — **не чіпаємо**.
4. З дня запуску Вікторія сама на Клубок не виставляє (дату — при запуску).

## Принципи
- **Шафа не змінюється.** `items.status` — лише Шафа. Клубок має **свою таблицю** зі своїм станом і id.
- **Без ШІ.** Поля Клубку рахує код з Картки (вона вже перевірена) і тексту поста.
- **Захист як у Шафи:** свій `guard` (клік, мережа), квиток на одну публікацію, підставний Клубок для тренувань. **На Клубку небезпечні дії — GET-посилання** (`/renew/all`, `?pg=renew-used`, `?pg=marksold`): guard блокує їх і для GET; навігація — лише за списком адрес.
- **Робот Клубку — окремий профіль Chrome** (`<дані>/klubok-profile/`), але **той самий замок** `robot.lock`: ніколи два Chrome одночасно (слабкий ноутбук).

## Що в Картці → що на Клубку (код, `src/shafa/klubok/fields.py`)
| Клубок | Звідки |
|---|---|
| Название (`item_name`, ≤ 100) | `title` Картки (формат той самий: «… N розміру в … стані») |
| Описание (`text`) | перше речення поста (без ціни) + порожній рядок + `description` Картки (її правки діють) |
| Стоимость | ціна **з поста** (`rules.price_from_text`), не ціна Шафи |
| Категорія (3–4 рівні) | таблиця «група + тип Шафи + сезон → шлях Клубку» (`klubok/category.py`), id — зі знімка |
| Пол (`sex`) | лише дитячі категорії (у дорослих поля немає): `rules.said_gender` — дівчинка 0, хлопчик 1, інакше 2 «Любой пол» |
| Состояние | «Новий» → 1 «Новое», інакше 0 «Б/у». «Сток» — ніколи |
| Размер (`size[]`) | цілі; піврозмір → обидва; значення мають бути в списку розмірів категорії |
| Цвет | перший колір Картки за таблицею UA → ключ Клубку; «Різнокольоровий» або ≥ 3 → 99; немає відповідника → не ставимо |
| Бренд | `brand` Картки; з підказки Клубку — пункт «Бренд (Кирилиця)», чий початок = бренд; немає — вільний текст (живу поведінку перевіряє KLB-003) |
| Фото | порядок Картки, ≤ 15, **по одному**, кожне після завершення попереднього; звірка порядку з `formData.images` |
| Характеристики, доставка, служби | не чіпаємо (за замовчуванням, як у неї) |

Чого не вистачає → Картка на Клубок не йде, причина-код (`klubok_no_category`, `klubok_size`, `klubok_no_price`, `klubok_title_long`). Шафи це не зачіпає.

## Таблиця категорій
Точна таблиця «група + тип Шафи + зима → лист Клубку (id)» — у коді `src/shafa/klubok/category.py` (зі знімка `categors.json` 10.11; назви шляху кожного листка там же, `klubok-catalog` відмовляється збирати знімок, якщо дерево на сайті змінилось). Решта (одяг, аксесуари крім сумок і гаманців) — v1 на Клубок не йде.

Рішення KLB-001 (Ітерація 1, 10.11): чоловічі сумки — за полем `gender` Картки «Для чоловіків» → `Мужское / Аксессуары / Мужские сумки` (1000990), гаманці/портмоне → `Портмоне, кошельки` (1000998); барсетки — завжди 1000990; малюки «Босоніжки» → «Летняя обувь» (1000391); авоськи, органайзери, кейси для косметики, косметички, аксесуари для сумок, картхолдери, ключниці, затискачі, візитниці → `klubok_no_category`. Тип «Сумки» з «маленьк…» у назві → «Клатчи и маленькие сумки». Кольори — лише таблиця в коді (`klubok/fields.py`), знімок їх не бере. Підказка бренду — єдине посилання, яке робот може натиснути: `a.dropdown-item` з `href="#"` усередині `#filter2` (`robot/klubok_guard.py`).

## База: версія 18 (KLB-002, критична)
Нові таблиці, наявні не змінюються (як версія 17):
- `klubok_ads` — рядок на Картку: `item_id` (PK, → items), `state` (`queued`, `publishing`, `published`, `problem`, `sold_asked`, `sold`, `removed`, `skipped`), `klubok_id` UNIQUE, `url`, `problem_code`, `problem_text`, `queued_at`, `publish_started_at`, `published_at`, `renewed_at`, `gone_at`, `sold_ok_at`, `removed_at`, `session_id`, `created_at`, `updated_at`.
- `klubok_listings` — знімок її оголошень на Клубку (id, назва, категорія, розміри JSON, бренд, ціна, фото, стан на Клубку, `post_id` — якщо надійно зіставлено, `asked_at` — уже показано в «Схоже, продано») + `klubok_listings_read` (коли читали).
- `sessions.site` (`shafa` | `klubok`, типово `shafa`) — сесії робота Клубку в тій самій таблиці; ліміт доби Клубку рахує `klubok_ads.publish_started_at`.

## Черга й ліміт (KLB-002)
- У чергу: Картки зі статусом Шафи `approved` / `publishing` / `published` (вона вже перевірила), з постом новішим за `KLUBOK_FROM_POST` (типово 7200), без рядка `klubok_ads` у стані `published`/`sold`/`removed`. Спершу зимове (сезон містить «Зима»), далі старіші пости першими.
- Ліміт доби `KLUBOK_DAILY_LIMIT` (типово 10, межі 1–30). Перша незрозуміла відповідь Клубку → стоп сесії + повідомлення Власнику (бот, `events.emit(..., loud=True)`).
- Дубль = блок акаунта, тому перед кожною публікацією:
  1. Ця Картка / цей пост уже має `klubok_id` → пропуск.
  2. Схожа на **її активне** оголошення (`klubok_listings`) або на **вже виставлене програмою** (той самий пост викладено вдруге) — правило як `robot/listings.find_duplicate` (тип + бренд + розмір ±0,5 + схожа назва) → `problem` `klubok_duplicate`, рішення її в Картці: «Інша пара — виставити» / «Так, дубль — не виставляти».
- Пост зник з каналу до публікації → `skipped` (`review.archive_gone` уже архівує Картку Шафи).

## Публікація (KLB-003, критична, жива — при Владі)
`robot --klubok-publish`: вхід руками (`--klubok-login`), знімок її активних (~1787) через `GET /api/get-items?user_id=198135&type=0&sort=date&limit=60&offset=N` (JSON: id, name, price, sold, moderated, renew_date…) → `klubok_listings`, потім черга. Форма додавання має живу reCAPTCHA v3 (`grecaptcha.execute` → `userItem.captcha`) — guard KLB-003 мусить пропускати запити `www.google.com/recaptcha/*`. Запис `publishing` до кліку «Опубликовать», успіх лише за id (відповідь `add-edit-used` → `used_id`, або адреса `/payment/{id}?action=used-submit-ok-logged` — на ній нічого не тиснути). Немає певної відповіді → `problem` `klubok_uncertain`, повтору немає. `/error429` (низька оцінка reCAPTCHA) → стоп сесії, повідомлення. Перші 1–3 — при Владі; запасний план: робот заповнює, «Опубликовать» тисне людина.

## «Обновить все» раз на 7 днів (KLB-004)
«Обновить все» = `GET https://klubok.com/renew/all` (посилання на `/users/198135/manage`, далі редирект туди ж; перевірено 10.11: 1787 активних оновились, наступне — через 7 днів, `renew_date` в `get-items`). Робот раз на добу: найраніший `renew_date` її активних ≤ зараз → один GET `/renew/all` за квитком → перечитати `get-items` і переконатися, що `renew_date` зсунулись; записати `renewed_at`.

## «Схоже, продано» (KLB-005)
- Джерело: `post_checks.gone_at` (нічна перевірка поста, вже є) і зникнення поста для `published` у `klubok_ads` → `sold_asked`, рядок у списку на екрані (вкладка «Проблеми» → блок «Клубок: схоже, продано»), кнопки «Так, продано» / «Ні, ще продається».
- Старі з 1786 без надійного поста — той самий список **один раз** (`klubok_listings.asked_at`).
- «Так, продано» → робот: «Пометить как проданное» (`/users/198135?pg=marksold&id={id}`), потім видалити в «Продане» → `removed`. «Ні» → більше не питати про це оголошення.

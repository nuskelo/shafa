# Як ми працюємо: Власник · Архітектор · Виконавець

Це опис процесу, який ми обкатали на проєкті crm-demo-stand: 99 PR, сервер у продакшені, чотири зовнішні команди.
Процес **не залежить від стеку** і від того, що саме будуємо. Змінюються лише назви перевірок, команди збірки і те, чи є сервер.

Документ написано для нового проєкту. **Прочитай його повністю перед першою відповіддю** і працюй за ним.

---

## 1. Ролі

| Хто | Де працює | Що робить | Чого НЕ робить |
|---|---|---|---|
| **Власник** (людина, Влад) | свій ноутбук, GitHub, сервер | Вирішує, що будуємо. Мержить PR. Запускає все на сервері. Переносить короткі фрази між чатами. | Не пише код. Не переносить великі тексти між чатами. |
| **Архітектор** (чат Claude у Cowork, з доступом до папки проєкту) | читає репозиторій через «міст», тобто доступ до папки на ноутбуці | Пише тікети. Читає дифф і звіти виконавця. Ухвалює технічні рішення. Дає Власнику команди для сервера (по одній, з поясненням). Пише листи стороннім людям. Веде стан проєкту. | Не комітить, не пушить, не мержить. Не робить `git checkout/pull/switch` у робочій копії: лише читання git. |
| **Виконавець** (Claude Code у VS Code на ноутбуці Власника) | робоча копія репозиторію | Пише код і тести. Комітить у гілку тікета, пушить гілку, відкриває PR, чекає перевірок, лагодить свої червоні. Пише звіт. | Не мержить. Не пушить у `main`. Не ходить на сервер (`ssh`/`scp`). Не чіпає `.github/` без явного дозволу. Не вирішує питань продукту чи безпеки сам. |

**Головний принцип.** Власник — не «кабель» між чатами. Великі тексти лежать у репозиторії, а через Власника йдуть лише короткі фрази.

## 2. Петля спілкування (найважливіше)

```
Архітектор ──(тікет у .claude/tickets/)──► репозиторій
     │
     └─► Власнику: «Скажи виконавцю: Візьми тікет .claude/tickets/XXX.md …»
                                │
Виконавець ◄────────────────────┘
     │  працює, на кожній зупинці пише звіт у .claude/handoff/XXX.md
     └─► Власнику: «Для Власника: <що зроблено> · Скажи Архітектору: <фраза>»
                                │
Архітектор ◄────────────────────┘
     сам читає handoff-файл і дифф через міст → рішення (ітерація в тікеті або «мерж»)
```

Правила петлі:

1. **Архітектор** кожне повідомлення з роботою для виконавця закінчує блоком **«Скажи виконавцю:»**: одна-три фрази, готові до копіювання.
2. **Виконавець** кожну зупинку (Фаза 0 готова, потрібне рішення, PR готовий) закінчує блоком
   **«Для Власника: <що зроблено, простою мовою> · Скажи Архітектору: <фраза>»**.
3. **Власник** пересилає лише фразу. Звіт Архітектор читає сам.
4. Рішення по Фазі 0 Архітектор дає або в тікеті (розділ «Ітерація N»), або коротким текстом «Скажи виконавцю: рішення по Фазі 0: 1) … 2) …».
5. **Новий тікет означає нову сесію виконавця** (`/clear`). Ітерації одного тікета йдуть у тій самій сесії.

## 3. Три ваги задач

Вагу називає Архітектор у тікеті.

| Вага | Що це | Папір | Фаза 0 |
|---|---|---|---|
| **Дрібниця** | ≤ ~30 рядків, без логіки: текст, конфіг, тег | без файлу тікета, одне речення через Власника | немає |
| **Звичайна** | усе між | бриф на один екран у `.claude/tickets/` | лише гіпотези (HYP), названі в брифі |
| **Критична** | безпека, секрети, доступи, дані користувачів, міграції БД, сервер, гроші, інтеграції з чужими API | повний тікет | **повністю, зупинка до коду** |

---

## 4. Фаза 0 — звірка з реальністю (до коду)

Навіщо: тікет пишеться з того, що Архітектор знає. Код і чужі API можуть виглядати інакше.
Фаза 0 ловить розбіжність **до того**, як написано 500 рядків не того.

Виконавець перед першим рядком коду:

1. знаходить усі файли, ендпоінти, поля, бібліотеки й API, які називає тікет;
2. кожну гіпотезу тікета позначає: **VERIFIED** (так і є) · **DRIFT** (інакше, з посиланням `файл:рядок` або виводом) · **UNKNOWN** (не перевірити без Власника чи сервера);
3. звіряє **з кодом і документацією, не з пам'яті**. Логіни, значення, дефолти бібліотек і ліміти API перевіряються запитом або читанням;
4. пише звіт у `.claude/handoff/<ID>.md` і **зупиняється**: «<ID> фаза 0 готова».

**Коли DRIFT зупиняє роботу.** Зупиняємось, якщо розбіжність міняє те, що треба збудувати, або вимагає вибору, якого виконавець не має права робити (модель даних, безпека, межа між частинами, відкрите питання). Якщо реальність лише безпечніша чи повніша за опис, а робота та сама, це записується у звіт, і робота триває.

При зупинці виконавець **не правити тікет сам** і **не адаптує архітектуру на свій розсуд**. Він чекає рішення.

## 5. Тікет — шаблон

Файл `.claude/tickets/<ID>-<коротка-назва>.md`. Пише лише Архітектор, а комітить виконавець разом зі своєю гілкою.

```markdown
# <ID> · <назва>

**Вага:** дрібниця / звичайна / критична. **Автор:** Архітектор · <дата>
**Гілка:** `feature/<ID>-<назва>` (або fix/ chore/ docs/) від `origin/main` після `git fetch`.

## Навіщо
1–3 речення: яку проблему закриває і що зміниться для користувача.

## Що зробити
Пронумеровано, конкретно. Кожен пункт — окремий коміт.

## Фаза 0 (якщо є)
- HYP-1: <твердження про код / API / поведінку>
- Що з'ясувати й записати в `.claude/handoff/<ID>.md`.
Після Фази 0 зупинись: «<ID> фаза 0 готова».

## Доказ (Definition of Done)
- тести, що доводять головне (і **червоніють**, якщо прибрати фікс);
- `make ci` зелений; на PR зелені обов'язкові перевірки.

## Для Власника (у звіті)
Які команди / дії потрібні від людини після мержу, по одній.

## Заборонено
`git pull` у main, пуш у main, мердж, `.github/`, сервер, <файли поза обсягом>.
Секрети — ні в код, ні в тести, ні у звіт.
```

**Префікси ID** (заводимо під проєкт), наприклад:

- `INF-` — репозиторій, CI;
- `CORE-` — основна логіка;
- `FIX-` — виправлення;
- `OPS-` — сервер, розгортання;
- `SEC-` — безпека;
- `QA-` — тестові прогони;
- `TD-` — борг;
- `DOC-` — документи.

**Обов'язок Архітектора перед тікетом.** Перелік файлів і гіпотези пишуться **з читання коду, а не з пам'яті**. Це три хвилини, а без них виконавець витратить цілий цикл на Фазу 0 і зупинку.

## 6. Звіт виконавця (handoff)

Файл `.claude/handoff/<ID>.md`, **10–15 рядків, максимум 40**. Оновлюється поверх на кожній зупинці.

```markdown
# <ID> — <стан: готово / зупинка на … / чекає …>
**Гілка:** … · **PR:** … · **Перевірки:** …
1. Фаза 0 (якщо була): HYP-N — VERIFIED / DRIFT / UNKNOWN, з файл:рядок.
2. Файли: створені й змінені.
3. Відхилення від тікета: з причиною — або «немає».
4. Нові TD / OPEN-Q: номери — або «немає».
5. Журнал: коміт із записом.
**Що потрібно:** <рішення, дія Власника або нічого>
**Для Власника:** <готові команди по одній, якщо потрібні>
```

Докази, таблиці й довгі виводи йдуть в опис PR або в коміти, не у звіт. Після мержу звіт переноситься в `.claude/archive/handoff/` першим комітом наступної гілки.

## 7. Git — правила (критично)

- **Лише гілки тікетів:** `feature/<ID>-…`, `fix/<ID>-…`, `chore/<ID>-…`, `docs/<ID>-…`. Прямих комітів у `main` немає ніколи.
- Гілка — **без upstream на main**: `git fetch && git switch -c <гілка> --no-track origin/main`, перший пуш `git push -u origin <гілка>`.
- Коміти дрібні, **Conventional Commits**: `feat:`, `fix:`, `test:`, `chore:`, `docs:`, `refactor:`.
- **Шлях у main — шість кроків:**
  1. гілка тікета, робота, запис у журнал останнім комітом;
  2. виконавець пушить **гілку** (Власник підтверджує кнопкою в IDE);
  3. виконавець відкриває PR;
  4. виконавець чекає перевірок на передньому плані й лагодить свої червоні;
  5. Архітектор читає дифф і каже «мерж»;
  6. **Власник мержить** на GitHub.
- **Заборонено без Власника:** `push --force`, `reset --hard`, `rebase`/`merge` у спільні гілки, видалення гілок і тегів, зміни CI (`.github/`), міграції проти реальної бази.
- **Захист у три шари:**
  - git-хуки в `.githooks/` (`pre-commit` не дає комітити в main, `pre-push` пускає лише гілки тікетів, без видалення й переписування історії; ставляться скриптом `ops/install-hooks.sh` на кожній копії);
  - дозволи Claude Code в `.claude/settings.json`: `git push` у `ask`, а `--force`, `--delete`, `--no-verify` у `deny`;
  - **захист гілки main на GitHub**: обов'язкові перевірки, заборона force-push і видалення, порожній bypass list.
- Ключ пушу для агента (`AGENT_PUSH=1` чи як назвемо) відчиняє лише гілку свого тікета і лише вперед.
- **Розгортання не автоматизується з CI.** Ключ від сервера в GitHub Actions перетворив би заборону «виконавець не ходить на сервер» на домовленість.

## 8. Перевірки (CI)

- Мінімум одна обов'язкова перевірка на PR, наприклад `quality`: лінт, типи, юніт-тести. Краще дві: друга — інтеграційні або браузерні тести.
- Локально — `make ci`: те саме, що в CI. Виконавець ганяє його перед пушем.
- Тест має доводити головне: **якщо прибрати фікс, тест червоніє.** Виконавець перевіряє це і пише у звіті.
- Для інтеграцій із чужими сервісами (Telegram, маркетплейси, AI) тести працюють із підставними відповідями (моки, фікстури), без мережі й без справжніх ключів.

---

## 9. Секрети й безпека

- **Секрети ніколи не пишуться** в чат, файли репозиторію, коміти, логи чи звіти. Це токени ботів, API-ключі, паролі, сесії Telegram, cookies маркетплейсу.
- Власник вводить секрет сам, «тихо», щоб його не було видно ні на екрані, ні в історії команд:
  ```
  read -rs TOKEN && printf 'TOKEN=%s\n' "$TOKEN" >> ~/.config/<проєкт>.env && unset TOKEN
  ```
  Файл лежить поза репозиторієм, з правами `chmod 600`.
- `.env.example` у репозиторії містить **лише назви** змінних, без значень.
- Публічні ключі пересилати можна, приватні ніколи.
- Архітектор ніколи не просить надіслати йому секрет у чат.

| Файл | Що там | Хто веде |

**Стан проєкту — у репозиторії, а не в пам'яті чату.** Новий чат Архітектора починає з читання `STATUS.md`, останніх записів журналу і `git log`.

## 11. Ритуали сесії виконавця

**Старт** (слова «продовжуємо», «поїхали», або назва тікета). Виконавець читає:

1. `CLAUDE.md`;
2. `STATUS.md`;
3. три останні записи журналу;
4. `TECH_DEBT.md`;
5. `OPEN_QUESTIONS.md`;
6. заголовки `LEARNED_CONVENTIONS.md`.

Потім перевіряє гілку, чистоту дерева і хуки. Перша відповідь починається рядком:

`[Pre-flight: CLAUDE ✓ | LEARNED ✓ | SESSION_LOG ✓ | TECH_DEBT ✓ | OPEN_Q ✓] гілка: <…>, тікет: <…>`

**Кінець** («на сьогодні все»): запис у журнал новим файлом, останнім комітом гілки. Дату брати командою `date`, а не з пам'яті.

## 12. Як Архітектор говорить із Власником

- **Українською, простою мовою, без жаргону.** Терміни пояснювати.
- **Команди для сервера чи терміналу — по одній**, кожна в окремому блоці, з тим, що має вийти. Кілька команд разом ламаються: інтерактивна команда «з'їдає» наступний рядок.
- Завжди уточнювати, **де** запускати: «на Mac» чи «на сервері (спершу `ssh …`)».
- Казати, коли **логічна пауза**, коли **мержити** і коли **нічого робити не треба**.
- Готові блоки: «Скажи виконавцю: …», листи стороннім людям, команди.
- Не стверджувати з пам'яті: спершу перевірити в коді через міст.
- Не казати «готово», поки результат не перевірено там, де він працює.

## 13. Як почати новий проєкт за цим процесом (перші тікети)

1. **Власник:** створює порожній приватний репозиторій на GitHub і клонує його на ноутбук. Підключає папку в Cowork, щоб Архітектор бачив її через міст. Відкриває її у VS Code з Claude Code.
2. **Архітектор:** розмова з Власником про продукт. Результат — `docs/concept.md`: навіщо, для кого, глосарій, що НЕ робимо, критерії готовності першої версії.
3. **INF-001 (риштування):** структура репозиторію, `CLAUDE.md` за розділами цього документа, `.claude/` (tickets, handoff, state, шаблон тікета), `Makefile` з `make ci`, лінт і тести, `.env.example`, `.gitignore`.
4. **INF-002 (захист):** git-хуки, `ops/install-hooks.sh`, `.claude/settings.json` з дозволами, CI-перевірка `quality`. **Власник** вмикає захист `main` на GitHub: Settings → Branches → обов'язкова перевірка, без force-push і видалення.
5. **Архітектор:** `docs/architecture.md`: модель даних, компоненти, змінні оточення, рішення (ADR одним рядком) і **окремим списком питання**, на які ще немає відповіді.
6. Далі CORE-тікети, по одній вертикальній функції за раз. **Результат кожного етапу — маленька робоча річ, а не половина всього.**

## 14. Уроки, які коштували дорого (переносимо)

- Факти про код, API й ліміти — **лише з читання чи досліду**, ніколи з пам'яті.
- Не казати «працює», поки не перевірено там, де воно працює насправді: на сервері чи з реальним API.
- Якщо щось висить або «магічно» ламається, спершу **ручна діагностика** з тими самими налаштуваннями і з виводом часу або кроків. Аж потім тікет.
- Тест, який не червоніє без фіксу, нічого не доводить.
- Великі зовнішні дані (архіви, образи, файли від інших людей) перевіряти **до** того, як їх «завантажити в систему»: вміст, контрольні суми, чужі імена.
- Залежності й образи закріплювати версією чи digest, а не плаваючим тегом.
- Робоча копія виконавця належить виконавцю. Архітектор у ній лише читає.

## 15. Додаток: що врахувати саме для проєкту «Telegram-канал → Шафа»

Це **питання для першої розмови й Фази 0**, а не рішення.

- **Читання каналу.** Бот (Bot API) бачить лише нові пости і лише якщо його додано адміном каналу. Історію каналу так не отримати. Для архіву потрібен клієнт користувача (MTProto, наприклад Telethon або Pyrogram) із сесією акаунта, а сесія — це **секрет** рівня пароля. Вирішити: лише нові пости чи й архів, і чий акаунт.
- **Шафа.** З'ясувати, чи є в Шафи офіційний API або імпорт (CSV/фід) для продавців, і що кажуть **правила Шафи** про автоматизацію. Публікація від імені акаунта через імітацію браузера крихка й може порушувати правила та призвести до блокування акаунта. Це питання для `OPEN_QUESTIONS.md` і рішення Власника до будь-якого коду публікації.
- **AI-розбір оголошення.** Текст і фото поста треба перетворити на поля: бренд, модель, розмір (EU/UA/см), стан, ціна, категорія Шафи, опис. Вирішити, яка модель, скільки коштує один пост і що робити, коли AI не впевнений.
- **Людина в петлі.** Рекомендую в першій версії **не публікувати автоматично**: програма готує чернетку, а знайома підтверджує одним натиском. Автопублікацію вмикати пізніше, коли розбір стане точним.
- **Фото.** Звідки брати (з поста), розмір і формат під вимоги Шафи, порядок.
- **Дублікати.** Пост редагують, видаляють, товар уже продано. Потрібна таблиця відповідності «пост ↔ оголошення на Шафі» зі станом.
- **Де працює.** Чи потрібен сервер (працювати 24/7), чи досить запускати на ноутбуці знайомої. Від цього залежать розділи про сервер і розгортання.
- **Перша вертикаль**, приклад: «один пост із каналу → чернетка з полями й фото в простій таблиці чи сторінці для перевірки». Без публікації. Це вже користь і перевірка точності AI.

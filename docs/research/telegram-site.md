# Telegram і пости каналу: факти для сайту (TG-001)

> 16.10.2026. Живий дослід на тестовому каналі (тип `channel`, з групою коментарів) і тестовому боті-адміністраторі.
> Бот мав права `can_post_messages`, `can_edit_messages`, `can_delete_messages` (на одну перевірку `can_edit_messages` вимикали).
> Bot API напряму (`getUpdates` з `allowed_updates` = `message`, `edited_message`, `channel_post`, `edited_channel_post`).
> Відповіді наведено дослівно. Ідентифікатори замінено: `<канал>`, `<група>` (група коментарів), `<людина>`.
> Тестові пости: № 24 — пост бота (текст); № 25 — пост людини руками (фото з підписом); № 26–27 — альбом людини; № 28 — пост бота, видалений.

## Коротко для команди сайту
1. Пост, опублікований людиною руками, приходить боту як `channel_post`. Правка приходить як `edited_channel_post`. **Про видалення Telegram не повідомляє ніяк.**
2. Свої власні пости бот як `channel_post` **не отримує**. Але якщо бот — адмін групи коментарів, кожен пост каналу (і свій теж) приходить туди як `message` з `is_automatic_forward: true` і `forward_origin.message_id` = номер поста.
3. За полями пост бота не відрізнити від поста людини: обидва мають `sender_chat` = канал і не мають `author_signature`. Відрізняти лише за власною базою.
4. Перевірка «пост є / видалено» — `editMessageReplyMarkup` з тим самим (порожнім) `reply_markup`. Є → `400 message is not modified`, видалено → `400 message to edit not found`. Пост не змінюється, позначки «змінено» немає, оновлень немає.
5. Ліміт: близько **20 перевірок існуючих постів за хвилину на канал**, далі `429 retry after N`. Перевірки видалених постів у ліміт не впиралися.

## b) channel_post
| Дія | Що прийшло боту | Висновок |
|---|---|---|
| бот: `sendMessage` у канал (№ 24) | `channel_post` **не прийшов**; у `<група>` прийшов `message` № 48: `from` = Telegram (777000), `sender_chat` = канал, `is_automatic_forward: true`, `forward_origin: {type: channel, chat: <канал>, message_id: 24}` | свої пости бот бачить лише через групу коментарів |
| людина публікує фото з підписом (№ 25) | `channel_post`: `message_id: 25`, `sender_chat` = `chat` = `<канал>`, `date`, `photo`, `caption`; **`author_signature` немає** (підписи в каналі вимкнені); + `message` у `<група>` з `is_automatic_forward` | ручні пости приходять |
| людина публікує альбом з 2 фото (№ 26, 27) | два `channel_post`: № 26 з `caption`, № 27 без; спільний `media_group_id: "14336793974210890"`; у групі — свій `media_group_id` | альбом = кілька оновлень, підпис на першій частині |
| людина редагує підпис № 25 | `edited_channel_post`: `message_id: 25`, `date` старий, `edit_date` новий, новий `caption`; + `edited_message` у `<група>` | правка приходить |
| бот: `deleteMessage` № 28 | **нічого**; копія поста в групі коментарів (№ 52) **лишилась** (прибирали окремо) | видалення не видно; копію в групі треба видаляти окремо |

Поля поста бота (відповідь `sendMessage`) і `channel_post` людини однакові за складом: `message_id`, `sender_chat`, `chat`, `date`, текст/фото. Ознаки «це бот» немає.

## c) Пересилання боту (у приватний чат)
| Як переслано | `forward_origin` | Висновок |
|---|---|---|
| 1. з каналу напряму | `{"type": "channel", "chat": {"id": <канал>, "title": …, "type": "channel"}, "message_id": 25, "date": 1792098806}` (+ старі `forward_from_chat`, `forward_from_message_id: 25`) | номер поста є |
| 2. з каналу → «Збережені» → боту | **те саме**, `message_id: 25` | від 1 не відрізнити |
| 3. створено в «Збережених» самою людиною → боту | **поля немає** (лише `caption`) | як звичайне повідомлення людини |
| 4. альбом з каналу напряму (і через «Збережені») | у кожної частини **свій** origin: `message_id: 26` і `27`; `media_group_id` новий (не той, що в каналі) | номер поста — в кожної частини |
| 5. з «Приховати ім'я відправника» | **поля немає** | зв'язок з постом втрачено |

## d) «Пост є / видалено»
Запит: `editMessageReplyMarkup {"chat_id": <канал>, "message_id": N, "reply_markup": {"inline_keyboard": []}}` (без `reply_markup` — та сама відповідь).

| Пост | `can_edit_messages` | Відповідь |
|---|---|---|
| № 24 бота | так / ні | `400 Bad Request: message is not modified: specified new message content and reply markup are exactly the same as a current content and reply markup of the message` |
| № 25 людини | так | те саме `message is not modified` |
| № 25 людини | **ні** | `400 Bad Request: message can't be edited` |
| № 28 видалений | так / ні | `400 Bad Request: message to edit not found` (так само для неіснуючого № 99999) |

- Після перевірок пост не змінився: позначки «змінено» немає, 2 перегляди, лічильника пересилань немає (дивився Власник у клієнті). `edited_channel_post` не приходив.
- **Обережно:** порожній `reply_markup` знімає кнопки, якщо вони в пості є. Для постів з кнопками треба передавати їхні поточні кнопки.

**Альтернатива** — `forwardMessage` / `copyMessage` у службовий чат (у досліді — приватний чат людини з ботом) з `disable_notification`, а потім `deleteMessage` копії:
| Пост | `forwardMessage` | `copyMessage` |
|---|---|---|
| № 24, № 25 | `ok`, нове повідомлення в службовому чаті (видалено одразу, `ok`) | `ok`, `{"message_id": …}` (видалено одразу, `ok`) |
| № 28 видалений | `400 Bad Request: message to forward not found` | `400 Bad Request: message to copy not found` |
- `copyMessage` працює і без `can_edit_messages`. У клієнті лічильника пересилань на пості не з'явилось. Статистику каналу (вона буває лише для великих каналів) не дивились.
- Мінуси: кожна перевірка створює і видаляє повідомлення в службовому чаті, тобто 2 запити замість 1. Ліміт для цього способу не міряли.

**Частота** (60 запитів `editMessageReplyMarkup` з паузою 1 с, по черзі № 24, № 25, № 28; ~78 с):
- запити 1–30 (20 перевірок існуючих) — без помилок;
- з 31-го (36-та секунда) кожна перевірка існуючого поста → `429 Too Many Requests: retry after 24` (далі 23, 21… 3), `parameters.retry_after` рахує до кінця хвилини;
- перевірки видаленого № 28 весь час → `400 message to edit not found`, ніколи не 429;
- з 61-ї секунди знову без помилок.
- Висновок: ≈ 20 перевірок існуючих постів за хвилину на канал (схоже на ліміт Telegram «20 повідомлень за хвилину в групу»). Отже 1300 постів — це ≈ 65 хв. Відповідь `429` не означає «є» чи «немає»: треба почекати `retry_after` і повторити.

## Рекомендація
- **Основний спосіб — `editMessageReplyMarkup` з тим самим `reply_markup`.** Один запит, нічого не створює, у каналі нічого не видно. Рішення беремо лише з двох відповідей: `message is not modified` → пост є; `message to edit not found` → видалено. Решту (`message can't be edited`, `429`, 5xx, обрив) вважаємо «невідомо, повторити пізніше» і **не** ставимо «Продано».
- Ботові сайту дати `can_edit_messages`, інакше для постів людини буде `message can't be edited`.
- Темп ≤ 15 перевірок за хвилину на канал. На `429` — пауза `retry_after`.
- `copyMessage` у службову групу без учасників — запасний спосіб.
- Нові пости: бот сайту має бути адміном каналу (`channel_post` — пости людини). Пости іншого бота (нашого) — див. «Не перевірено».

## Не перевірено
- **Вік поста > 48 год.** Тестові пости свіжі (15.10 23:52 і 16.10 00:13). **Нагадування: 18.10.2026 після 01:00 повторити d) на № 24, 25, 28.** Пости в тестовому каналі для цього лишено.
- **Чи отримує бот сайту `channel_post` на пости, які опублікував інший бот (наш).** Свої пости бот не отримує. Для чужого бота другого тестового бота не було. Запасний шлях: копії постів у групі коментарів (`is_automatic_forward`), які бачить бот-адмін групи. Перевіряти з ботом сайту в тестовому каналі.
- Ліміт для `copyMessage` / `forwardMessage`; поведінка з кількома каналами одночасно.
